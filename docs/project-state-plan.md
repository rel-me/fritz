# Project and thread state redesign

Use one app-owned SQLite database for projects, threads, and transcript entries. Open a thread on its newest page, fetch older entries by sequence as the user scrolls, and write only rows affected by the current action. Keep the amount of work bounded from disk through the SwiftUI view and through the request sent to the chat harness.

## What Fritz does today

[AppDatabase](../app/Sources/Fritz/Stores/AppDatabase.swift) already stores a SQLite row per message. Nevertheless, it reads a whole thread on open and deletes and reinserts all its messages on send, tool events, and completion. Selecting or renaming a thread saves all project and thread metadata. [WorkspaceStore](../app/Sources/Fritz/Stores/WorkspaceStore.swift) retains every opened chat, and [ChatView](../app/Sources/Fritz/Views/ChatView.swift) eagerly measures every loaded message. [ChatStore](../app/Sources/Fritz/Stores/ChatStore.swift) builds each request from its full in-memory transcript. The harness can compact context later in the request path, after the app has already assembled and transferred it.

JSONL can be fast for appends and a bounded tail read that seeks backward in chunks. Large individual lines make even a tail read variable in size. Stable random access, archive and delete operations, and atomic updates involving drafts, turns, and sidebar metadata would require additional indexes or coordination. SQLite gives Fritz indexed ranges and transactions in the same store. Keep newline-delimited JSON for the private pipe protocol. [SQLite scrolling-window queries](https://www.sqlite.org/rowvalue.html#scrolling_window_queries)

## Storage and ownership

Use a fresh `projects.sqlite` under the existing Fritz data directory. Start with an empty workspace and preserve the previous files on disk. Skip import, migration from the old project schema, and dual writes. Keep the existing settings API and its persisted values in `workspace.sqlite`, with a settings-only path that skips project restore and data-wide validation. On a clean profile, initialize app settings with their existing defaults. Keep provider, credential, model-location, and browser storage independent. A project may have a folder reference. Folder repair changes future action scope while preserving thread IDs and history. Deleting records leaves user folders and their contents alone.

| Record | Proposed shape |
| --- | --- |
| Projects | Stable ID, name, optional normalized folder, creation time, stable sidebar sort key. Enforce unique non-null folder references. |
| Threads | Stable ID, project foreign key, title and automatic-title flag, archive state, timestamps, stable sidebar sort key, next entry sequence. Index by project, archive state, sort key, and ID, with an index for the combined active and archived view. |
| Workspace navigation | Selected thread ID as a nullable foreign key. Resolve its project directly on startup, even if either lies outside the first sidebar page. |
| Thread preferences | One row per thread for the draft, provider connection ID, model ID, reasoning, and speed. Resolve display metadata from the model catalog. |
| Transcript entries | One row per visible user or assistant message, keyed by `(thread_id, sequence)`, with a stable entry ID, turn ID, role, status, timestamp, and display text or a body reference. Sequence is monotonic, allocated transactionally, and kept across clear operations. |
| Tool activity and payloads | Ordered records keyed to their assistant entry, with tool metadata and separate arguments and result bodies. Read only a compact per-message activity summary with a message page and load details on demand. Store large message bodies separately from bounded previews, with chunked access when needed. |
| Model context | A derived per-thread checkpoint through a committed turn sequence, plus a bounded recent suffix assembled from durable context records. Preserve typed tool exchanges wherever the harness can replay them. Store opaque provider context separately with provider/model provenance if replay requires it. |

Keep the native app as the workspace owner. Reuse the low-level Swift SQLite layer where it fits. Run DB open, queries, decoding, and writes off the main actor. Use one serialized writer and short reads with WAL; use a read connection separate from the writer if measurement shows write contention in foreground reads. Keep schema and version checks on open, and move whole-database integrity and foreign-key scans to diagnostics. Start with WAL synchronous FULL for the project writer so committed sends and terminal records survive a power loss on supported storage. Measure that cost along with checkpoint latency and WAL growth under load. [SQLite WAL behavior](https://www.sqlite.org/wal.html)

## Read and write paths

- **Launch and sidebar.** Fetch the first 50 project headers, resolve the restored selection by ID, and fetch the first 50 thread headers only for the selected or expanded project as needed. Page by the last stable sort key and ID. Preserve the current ordering initially so ordinary activity does not invalidate cursors. Push archive filtering into SQL. Probe folder availability off the main actor for visible and active projects, and revalidate before dispatching folder actions. Cancel or ignore stale page results after a selection, filter, or data revision changes.
- **Transcript.** Read the newest 40 entries in descending sequence and display them chronologically. Fetch the next page with `WHERE thread_id = ? AND sequence < ? ORDER BY sequence DESC LIMIT ?`. Start with a 256 KiB display payload budget per page and bound individual previews. Load tool bodies and large message bodies separately. Preserve the visible entry and pixel offset when prepending, preserve follow-at-bottom during streaming, and keep a bounded row window that can page in either direction. Keep a byte-bounded cache for inactive conversations and retain active runs independently of view eviction.
- **Changes.** Use commands such as rename, select, archive, append, checkpoint, and complete. Each writes the affected records only. In one send transaction, append the prompt, record the pending assistant entry, clear the draft, and set the automatic title if needed. Dispatch only after commit and reuse the turn ID on storage retries. Coalesce partial response writes by interval and size (start with 500 ms or 64 KiB of new data, whichever comes first), persist tool receipts promptly, and make terminal status and usage atomic. Avoid copying the entire accumulated body per flush for oversized answers. Debounce drafts independently and flush or surface failures on switching and normal quit.
- **Recovery.** Scope writes by thread and active turn ID. Serialize archive, clear, delete, and folder repair against active runs, invalidate their turn IDs before applying late callbacks, and use foreign keys for owned records. On reopen, show pending turns as interrupted with their last durable content and any tool receipt. An unfinished tool call has an unknown outcome. Preserve that fact and never replay a provider request or folder action automatically after a crash. Surface failed writes and allow explicit recovery from the last committed state. Use stable IDs and uniqueness constraints to prevent duplicate records on retries.

## Context for the next model request

The visible page is for reading the conversation. Build the model request from SQLite using a checkpoint of older readable history and a bounded suffix of complete turns. Set explicit byte and token budgets before serialization, reserve output and tool headroom, and apply the chosen model's context limit, including local models. Keep tool-call/result pairs together; if the current prompt or a required exchange cannot fit, surface a size error. Check the request before clearing the draft and reserve the same turn ID if dispatch fails after commit. Store the checkpoint's source sequence and format version and invalidate it on clear or any operation that changes its source history. Advance it incrementally from committed records and allow a bounded, restartable rebuild. Treat summaries as untrusted conversation data and keep the full transcript available for reading.

The current [app chat request](../src/provider.rs) carries role/content strings. Swift renders persisted tool details into text for later requests, while the Rust harness maintains native tool exchanges inside a running request. Extend the private chat protocol and harness to carry validated, versioned tool exchange records across requests. Cover both interrupted and completed work, and define a readable projection when changing providers so foreign opaque state never crosses provider boundaries. Preserve cancellation and per-chat process ownership.

## Delivery and acceptance

1. Build the fresh repository and verify indexed queries, targeted transactions, boot behavior, and isolation from app settings on fresh and existing profiles.
2. Wire sidebar and transcript windows to the repository. Verify selection across pages, archive filters, scroll anchors across window resize, Markdown reflow, and switching away from an active response.
3. Wire durable turns, then bounded context across the app, agent, and harness. Use the mock provider to exercise tool execution and replayed context data, cancellation, provider changes, and quit/relaunch. Ship the cutover only after these steps work together.
4. Profile the staged app on a documented reference Mac with synthetic data. Include 5,000 projects, 100,000 threads overall, one 100,000-entry thread, large bodies and tool results, and multiple streams. Compare against a small fixture using the same page sizes. Initial targets are warm p95 below 50 ms for a repository page, p95 below 200 ms from selecting a thread to a usable recent transcript once the app is open, and no main-thread stalls over 50 ms caused by storage or decoding. Record cold launch separately. Check that a deep page has index-range access, writes touch only affected records, memory plateaus after repeated switches and scrolls, and request bytes stay under the chosen budget. Test disk-full and lock contention, kill during send and a tool run, and crash or cancel while archiving or deleting. Verify drafts, selection, tool outcomes, and the empty-workspace cutover on relaunch. [Runtime verification](agents/runtime-verification.md) · [UI verification](agents/ui-verification.md)

Defer workspace-wide full-text search and database sharding. Add an FTS index when search is requested and measure its write and disk cost. Revisit sharding if measured single-writer contention remains after short transactions and batched streaming writes.

## Design review

- **A SQL limit is insufficient by itself.** Startup integrity scans, a transcript page containing a giant result, and the eager SwiftUI stack can each dominate latency. Verify bytes read and decoded, view memory, and main-thread time as well as returned row count.
- **A fast transcript can still produce a slow send.** Require bounded requests and a compaction checkpoint before cutover. Test exact call/result pairing across a crash and across the app-to-harness boundary, where the current protocol flattens prior tool records.
- **Background work can outlive its view.** Qualify async reads by selection and revision; qualify writes by turn ID. Test rapid switching, late events after deletion, and shutdown with a dirty draft and a pending reply.
- **A fresh workspace is a product-visible reset.** Document the first-launch behavior and retained files. Test that old project records stay untouched and that app settings, saved providers, and model locations still resolve.
- **Performance targets are acceptance criteria.** The plan review can check index shape and ownership now. The staged app must establish latency, memory, and durability before sign-off.
